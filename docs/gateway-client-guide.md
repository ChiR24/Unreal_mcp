# Gateway client guide — one tool, four operations

How a client configures this server, discovers a capability, and executes it.

Every claim below names the file that implements it. If you cannot find the
behavior at the cited path, treat this document as wrong and fix it — the docs
contract in `tests/unit/docs/docs-claim-contract.test.ts` exists to catch
exactly that drift.

## The public surface is one tool

Both transports expose exactly **one** public MCP tool, `unreal`. There is no
opt-out on either surface: the TypeScript `MCP_GATEWAY_MODE` env var and the
native `bEnableNativeGateway` project setting were both removed.

`tools/list` returns `{ "unreal" }` and never changes shape, so
`notifications/tools/list_changed` is suppressed on both surfaces
(`src/server/tool-registry.ts`, plugin `Private/MCP/DynamicTools`).

The 23 canonical parent tools are an **internal routing boundary**
(`handleConsolidatedToolCall()` in
`src/tools/orchestration/consolidated-handler-dispatcher.ts`). They are not a
client-visible listing and there is no legacy multi-tool listing to restore.

| Operation | Purpose | Implementation |
| --- | --- | --- |
| `search` | Find capabilities by query and filters | `src/server/gateway/gateway-search.ts` |
| `describe` | Drill one level into a contract | `src/server/gateway/gateway-describe.ts` |
| `execute` | Run one validated action | `src/server/gateway/gateway-execute.ts` |
| `configure` | Internal tool enable/disable (`manage_tools`) | `src/server/tool-registry-gateway.ts` |

Reference tables generated from the records themselves:

- [`action-reference.generated.md`](action-reference.generated.md) — every
  capability, its effect, required scope and consent mode.
- [`migration-reference.generated.md`](migration-reference.generated.md) — every
  legacy `{tool, action}` pair and what it resolves to.

Both are regenerated by `npm run registry:generate` and gated by
`npm run registry:check`. Do not hand-edit them.

## Client configuration

Two transports, two lifecycles. Pick one; do not route between them.

### Native MCP (Streamable HTTP/SSE, no Node.js)

The plugin serves MCP directly. `GET /mcp` opens SSE, `POST /mcp` carries
JSON-RPC, `DELETE /mcp` tears down a session. Default port `3000`, overridable
with `MCP_NATIVE_PORT`.

```json
{
  "mcpServers": {
    "unreal-engine": { "type": "url", "url": "http://localhost:3000/mcp" }
  }
}
```

### TypeScript stdio bridge

`node dist/cli.js` connects to the plugin's WebSocket listener (loopback
`8090,8091` by default) and speaks MCP over stdio.

```json
{
  "mcpServers": {
    "unreal-engine": {
      "command": "node",
      "args": ["path/to/Unreal_mcp/dist/cli.js"],
      "env": { "UE_PROJECT_PATH": "C:/Path/To/YourProject" }
    }
  }
}
```

Both surfaces bind loopback-first. Non-loopback requires an explicit opt-in
(`MCP_AUTOMATION_ALLOW_NON_LOOPBACK` for the Node process,
`bAllowNonLoopback` for the plugin's own listeners) and, on the native
transport, `bRequireCapabilityToken` as well — the native transport refuses to
bind non-loopback without it. See [`security-and-receipts.md`](security-and-receipts.md).

### Which engine you can actually run this against

The plugin's build scope spans nine UE minors, but that scope is a build
target, not a test result. Of the nine, **one** has a passing live record
(5.7.4) and that record is stale against the current tree; one (5.8 Preview 1)
does **not** compile today; and the remaining seven could not be tried on the
recording host, so their compatibility is unknown rather than broken.

Read the per-minor table in
[`performance-and-evidence.md`](performance-and-evidence.md#the-nine-advertised-minors)
before you pick an engine. Do not infer support for a minor from the badge
range.

## Protocol version negotiation is asymmetric on purpose

The native `/mcp` transport supports exactly three versions
(`McpSupportedProtocolVersions` in
`plugins/.../Private/MCP/Transport/McpNativeTransportPrivate.h`):

- `2025-11-25` (latest)
- `2025-06-18`
- `2025-03-26`

The TypeScript stdio server negotiates through the MCP SDK's
`SUPPORTED_PROTOCOL_VERSIONS`, which **additionally** accepts two legacy
versions: `2024-11-05` and `2024-10-07`.

So a client pinned to a legacy version negotiates with the TypeScript surface
but not the native one. The native surface is intentionally stricter.

> The native transport deliberately does **not** implement any release
> candidate later than `2025-11-25`. Do not describe one as supported.

Full negotiation and header-guard behavior: [`protocol.md`](protocol.md).

## Discovery is progressive, never a schema dump

`describe` drills exactly one level per call and `perActionSchemas` is always
`false` (`src/server/gateway/gateway-describe.ts`):

| Call | Returns |
| --- | --- |
| `describe {}` | the domain list |
| `describe { domain }` | that domain's families |
| `describe { domain?, family }` | the capabilities in the family |
| `describe { capability }` | one exact contract |
| `describe { capability, param }` | one parameter's schema |
| `describe { tool }` | parent summary + action list, no `inputSchema` body |
| `describe { tool, action }` | the parameter catalog for that pair |
| `describe { tool, action, param }` | one parameter's full schema |

The `{ tool, action }` parameter catalog is the **tool-union**: parameters are
shared across all actions of the parent tool, not action-specific. Per-action
schema maps do not exist on this surface.

Every invalid selector returns a structured guided error carrying closest-match
`suggestions` plus an executable `nextCall` that drills one level deeper
(`closestMatches()` / `buildNextCall()` in
`src/server/gateway/gateway-guidance.ts`, `MAX_SUGGESTIONS = 3`).

## The two execute request forms

`resolveExecuteTarget()` in `src/server/gateway/gateway-execute-resolve.ts`
accepts two forms, and **neither wins by precedence**.

**Canonical (v2)** — preferred for new clients:

```json
{
  "operation": "execute",
  "capability": "manage_asset.import_asset",
  "params": { "sourcePath": "/tmp/mesh.fbx", "destinationPath": "/Game/Imported/mesh" }
}
```

**Legacy** — the pre-gateway `{tool, action}` spelling, generated from each
record's `legacyIds`:

```json
{
  "operation": "execute",
  "tool": "manage_asset",
  "action": "import_asset",
  "params": { "sourcePath": "/tmp/mesh.fbx", "destinationPath": "/Game/Imported/mesh" }
}
```

Rules the resolver enforces:

- Supplying **both** forms is allowed only when they designate the same
  capability. Disagreement is a `FORM_CONFLICT` refusal, never a silent pick.
- Supplying **neither** is `MISSING_SELECTOR`.
- An alias resolves visibly; an alias owned by more than one capability is
  `ALIAS_CONFLICT` rather than a guess.
- Unknown selectors return `UNKNOWN_CAPABILITY` / `UNKNOWN_TOOL` /
  `UNKNOWN_ACTION`, each with `suggestions` and an executable `nextCall`.

## Deprecation and removal behavior

Three distinct removal behaviors exist. They are not interchangeable.

### 1. A direct call to a canonical tool name

A `tools/call` whose `name` is not `unreal` is **not routed**. It returns a
bounded, copy-paste-executable `DIRECT_TOOL_CALL_REMOVED` receipt
(`src/server/gateway/direct-call-migration.ts`; the native transport emits the
same shape from `McpNativeTransportGateway.cpp`). The receipt's `nextCall`
drills exactly one level:

| Situation | `nextCall` |
| --- | --- |
| unknown tool name | `{ "operation": "search" }` |
| known tool, no action | `{ "operation": "describe", "tool": "<tool>" }` |
| known tool with an action | `{ "operation": "execute", "tool": "<tool>", "action": "<action>", "params": { … } }` |

The migrated `params` are the original arguments with the nested `params`
wrapper flattened (top-level keys win) and the control fields `action`,
`subAction`, `params`, `operation` removed. Re-running the `nextCall` through
`unreal` completes the migration.

### 2. A retired verb (`CAPABILITY_REMOVED`)

Eight legacy routes are explicit **typed removals** — verbs whose bodies were
proven to be no-ops or unreachable. They are listed with their guidance in
[`migration-reference.generated.md`](migration-reference.generated.md).

Executing one returns `CAPABILITY_REMOVED` with the removal guidance
(`checkMigration()` in `gateway-execute-resolve.ts`). A `removed` disposition is
a hard failure: **do not fall back to the old behavior.**

### 3. A lossy legacy shape (`MIGRATION_NON_TRANSLATABLE`)

Where a legacy call cannot be mapped without dropping meaning, translation is
refused rather than coerced. The curated rule set lives in
`src/tools/catalog/capabilities/migration/lossy-translations.ts`.

The shipped example: `set_volume_bounds` carrying a `bounds.origin` historically
had its origin silently dropped when coerced to `set_volume_extent`. It now
refuses, returning replacement guidance naming `set_volume_extent`.

> `LOSSY_RULES` is **curated, not exhaustive**. Only rules with leaf-body
> evidence are encoded. Other silent-drop coercions may remain in the legacy
> handler surface; absence from this list is not proof of losslessness.

## Execute error codes

| Code | Raised by |
| --- | --- |
| `FORM_CONFLICT`, `MISSING_SELECTOR`, `ALIAS_CONFLICT` | form resolution |
| `UNKNOWN_CAPABILITY`, `UNKNOWN_TOOL`, `UNKNOWN_ACTION` | selector lookup |
| `CAPABILITY_REMOVED`, `MIGRATION_NON_TRANSLATABLE` | migration check |
| `UNREAL_EXECUTION_ERROR`, `OUTPUT_SCHEMA_VIOLATION`, `RESULT_TOO_LARGE` | dispatch and output validation |
| `DIRECT_TOOL_CALL_REMOVED` | a `tools/call` on a non-`unreal` name |

Authorization refusal codes are shared verbatim with the plugin and are
documented in [`security-and-receipts.md`](security-and-receipts.md).
