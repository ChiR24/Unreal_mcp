# Gateway client guide — one tool, four operations

How a client configures this server, discovers a capability, and executes it.

Every claim below names the file that implements it. If you cannot find the
behavior at the cited path, treat this document as wrong and fix it.

## The public surface is one tool

The plugin serves exactly **one** public MCP tool, `unreal`, at `/mcp`; the npm
package is a stdio proxy that relays to it. There is no opt-out: the native
`bEnableNativeGateway` project setting was removed.

`tools/list` returns `{ "unreal" }` and never changes shape
(`Private/MCP/Gateway/McpNativeGatewayDefinition.cpp`).

The 23 canonical parent tools are an **internal routing boundary**: `execute`
runs `{ action, ...params }` on the record's parent tool
(`Private/MCP/Execute/McpNativeTransportGatewayExecute.cpp`). They are not a
client-visible listing and there is no legacy multi-tool listing to restore.

| Operation | Purpose | Implementation (`plugins/.../Private/MCP/`) |
| --- | --- | --- |
| `search` | Find capabilities by query and filters | `Gateway/McpNativeGatewaySearch.cpp` |
| `describe` | Drill one level into a contract | `Gateway/McpNativeGatewayDescribe*.cpp` |
| `execute` | Run one validated action | `Execute/McpNativeTransportGatewayExecute.cpp` |
| `configure` | Internal tool enable/disable (`manage_tools`) | `DynamicTools/McpDynamicToolManager.cpp` |

The reference table [`action-reference.generated.md`](action-reference.generated.md)
lists every capability, its effect, required scope and consent mode. It is
regenerated by `npm run registry:generate` and gated by `npm run registry:check`.
Do not hand-edit it.

## What a model reads before its first call

Wrong calls mostly come from guessed names, so the guidance a client sees before
it calls anything is treated as part of the contract:

- **Tool description** — `McpNativeGatewayDefinition.cpp` states the search ->
  describe -> execute order, the copy-the-`nextCall` rule and the `params` rules,
  beside the input schema.
- **`instructions` at `initialize`** — the transport reads them from
  `Resources/MCP/server-info.json` (plus the project's **Server Instructions**
  setting); the proxy hands the same text on and adds one line about itself.
  Most hosts inject it into the model's system prompt once per session, so it
  holds the longer version: workflow, error-code recovery and path conventions.
- **Every response carries a next step** — search rows, describe replies and
  guided errors all include an executable `nextCall`; an empty search page says
  how to rephrase and points at `describe {}`; a `{ tool }` summary points at a
  filtered `search` via `browse`.
- **Search vocabulary lives on the records** — `discovery.topics` is the
  highest-weighted free-text ranking field, so a capability declares the
  phrases a caller types (`topics: ['spawn actor', 'place actor']` on a builder
  spec, or `withTopics()` from `records/utility/helpers.ts` for the positional
  builders). `tests/eval/plain-probe.data.ts` lists the plain-language phrasings
  that must rank the intended capability first.
- **A verb the action name does not carry is a declared alias** — `topics` alone
  cannot outrank a record whose action name IS the verb (`asset.move` beats
  every "move actor" phrasing), so such a record declares an alias id
  (`aliases: ['control_actor.move_actor']`). Search counts a record's own
  aliases as its names (`Private/MCP/Gateway/McpNativeGatewaySearchMatch.cpp`),
  and the alias resolves on `describe` and `execute` exactly like the canonical
  id, so a model that guesses it lands on the right capability. Question words
  are function words, so "how do i spawn an actor" ranks like "spawn actor".
- **A name callers keep inventing becomes an alias** — `scripts/mine-invented-names.mjs`
  reads Claude Code transcripts, pairs each `UNKNOWN_ACTION` / `UNKNOWN_CAPABILITY`
  name with the call that then worked, and proposes the ones two or more sessions
  agree on (`system_control.restart_editor` for `control_editor.restart_editor`).
  A person approves the list; the plain-request probes check that none moves a
  first hit. A name for one variant of a family is an `aliasMembers` entry that
  pins its selector value (`connect_nodes` for `edit_graph`'s `connect_pins`).

## Client configuration

### Native MCP (Streamable HTTP/SSE, no Node.js)

The plugin serves MCP directly, on by default (**Enable Native MCP Server**).
`GET /mcp` opens SSE, `POST /mcp` carries JSON-RPC, `DELETE /mcp` tears down a
session. Default port `3000`, overridable with `MCP_NATIVE_PORT`.

```json
{
  "mcpServers": {
    "unreal-engine": { "type": "url", "url": "http://localhost:3000/mcp" }
  }
}
```

### stdio proxy (Node.js)

`node dist/cli.js` (or `npx unreal-engine-mcp-server`) speaks MCP over stdio and
relays to the same `/mcp` (`src/proxy/native-proxy.ts`). While the editor is
down every call answers `NOT_CONNECTED`; the first call after it is back opens
a new upstream session, so the client never reconnects. It reads the capability
token from `UE_PROJECT_PATH` and points at `UNREAL_MCP_URL`.

```json
{
  "mcpServers": {
    "unreal-engine": {
      "command": "node",
      "args": ["path/to/Unreal_mcp/dist/cli.js"],
      "env": { "UE_PROJECT_PATH": "C:/Path/To/YourProject" }
    }
  }
}
```

The plugin binds loopback-first. Non-loopback requires `bAllowNonLoopback` and,
on the native transport, `bRequireCapabilityToken` as well — the native
transport refuses to bind non-loopback without it. See [`security-and-receipts.md`](security-and-receipts.md).

### Which engine you can actually run this against

The plugin's build scope spans nine UE minors, but that scope is a build
target, not a test result. Of the nine, **one** has a passing live record
(5.7.4) and that record is stale against the current tree; one (5.8 Preview 1)
does **not** compile today; and the remaining seven could not be tried on the
recording host, so their compatibility is unknown rather than broken.

Read the per-minor table in
[`performance-and-evidence.md`](performance-and-evidence.md#the-nine-advertised-minors)
before you pick an engine. Do not infer support for a minor from the badge
range.

## Protocol version negotiation

The native `/mcp` transport supports exactly three versions at `initialize`
(`McpSupportedProtocolVersions` in
`plugins/.../Private/MCP/Transport/McpNativeTransportPrivate.h`), and the proxy
negotiates the same three:

- `2025-11-25` (latest)
- `2025-06-18`
- `2025-03-26`

A client asking for another version, such as the legacy `2024-11-05`, is
answered with `2025-11-25`, as the spec says; it may then disconnect.
`2026-07-28` requests carry their own version and need no `initialize` or
session.

Full negotiation and header-guard behavior: [`protocol.md`](protocol.md).

A consent grant from `describe` carries a single-use `nonce`, minted for that
capability and required: the same grant sent again is refused with
`CONSENT_REUSED`, and a grant whose nonce this server did not mint for the
capability (missing, made up, or too old) with `CONSENT_NOT_ISSUED`. A refused execute carries its typed
error as `typedError`, and `maxBytes` counts the result rows.

## Discovery is progressive, never a schema dump

`describe` drills exactly one level per call
(`Private/MCP/Gateway/McpNativeGatewayDescribe*.cpp`). `perActionSchemas` is
`false` only on the `{ tool }` summary; every capability-level answer reports
`true`:

| Call | Returns |
| --- | --- |
| `describe {}` | the domain list |
| `describe { domain }` | that domain's families |
| `describe { domain?, family }` | the capabilities in the family |
| `describe { capability }` | one exact contract |
| `describe { capability, param }` | one parameter's schema |
| `describe { tool }` | parent summary + action list (every name unless `limit` is sent, no `inputSchema` body) + a `browse` call: `search` filtered to that tool, whose rows carry per-action summaries |
| `describe { tool, action }` | the exact contract of the capability that pair resolves to |
| `describe { tool, action, param }` | one parameter's full schema |

The three browse levels show 50 rows unless `limit` is sent; `offset` pages
every listing.

`describe { tool, action }` resolves the legacy pair to its canonical record
(`McpNativeGatewayDescribe.cpp`) and returns
that action's exact contract: `inputSchema` lists only the parameters the action
declares, never the parent tool's union. Only the `{ tool }` summary is still a
legacy view, which is why it also carries `browse`.

### A clear first hit can skip describe

When search's first row is clear (the runner-up scores at most 90% of it) and
needs no consent, it also carries `signature` and `executeCall`. `signature`
holds the `required` parameters' types (or values), an `oneOf` group, a
family's `selector` (`name`, `values`, `default`) and one `example`;
`executeCall` is the execute call describe would hand over. Fill `params` from
the signature and send `executeCall`, or describe first for the full contract.
`tests/eval/confident-hit.test.ts` holds that rule to 95% precision.

### A typo is read as the word it was meant to be

A query word that no record's action words, aliases, topics, family, domain,
parent or summary carry (so it could match nothing) is replaced by the nearest
word that names a capability, and the reply lists each replacement in
`corrected` (`[{ from: "spwan", to: "spawn" }]`). Nearest means fewest edits: a
swap of two letters, a missing or extra letter, or a slip onto a neighbouring
key costs one; any other substitution costs two, since that is where real words
meet ("carve" stays "carve", it is not "curve"). Words of 5-7 letters take one
edit, 8 or more two, 4 letters only a swap ("lsit"); shorter words, words with
digits and function words are never changed. On the plain-request probes no
correctly spelled request is rewritten, and one typo per request keeps the
first hit right in 95% of them (33% uncorrected).

### Folded families

Most capabilities are **families**: one record advertising one action whose
selector parameter (`kind`, `edit`, `setting`, `info`, ...) picks the
operation, so `manage_asset.create_texture { kind: "noise" }` is what the
catalog used to call `create_noise_texture`. Nothing was retired:

- `describe { tool: "manage_asset", action: "create_noise_texture" }` still
  works and returns the family's contract; `execute` with that old pair still
  runs the old handler, because the pair pins the selector value it implied
  (`kind: "noise"`). A caller-supplied value is never overridden.
- The former capability ids (`texture.create_noise_texture`) are declared
  aliases of the family, so the canonical form accepts them too. So are the
  aliases a member declared, and each runs that member as its old pair does
  (`blueprint.add_component_to_blueprint` is `add_scs_component`, with
  `edit: "add_scs_component"` pinned).
- A family whose primary is one of its members keeps the selector optional and
  defaults it to that member (`manage_asset.list` without `kind` still lists
  assets). A family under a new name requires the selector; `describe` shows
  it as required with its enum.
- The selector parameter's description lists every variant with what it does,
  its defaults, replies and refusals included, one line each as
  `value: summary`; a sibling action named there appears as the selector value
  to send (`setting=vsync`).
- A consent grant may name the capability by its canonical id, an alias, or a
  folded `tool.action` pair; `describe` always returns the canonical grant.

Every invalid selector returns a structured guided error carrying closest-match
`suggestions` (at most 3) plus an executable `nextCall` that drills one level
deeper (`Private/MCP/Gateway/McpNativeGatewayGuidance.cpp`).

## The two execute request forms

Execute (`Private/MCP/Execute/McpNativeGatewayExecuteRequest.cpp`) accepts two
forms, and **neither wins by precedence**.

**Canonical (v2)** — preferred for new clients:

```json
{
  "operation": "execute",
  "capability": "manage_asset.import_asset",
  "params": { "sourcePath": "/tmp/mesh.fbx", "destinationPath": "/Game/Imported/mesh" }
}
```

**Legacy** — the pre-gateway `{tool, action}` spelling, generated from each
record's `legacyIds`:

```json
{
  "operation": "execute",
  "tool": "manage_asset",
  "action": "import_asset",
  "params": { "sourcePath": "/tmp/mesh.fbx", "destinationPath": "/Game/Imported/mesh" }
}
```

Rules the resolver enforces:

- Supplying **both** forms is allowed only when they designate the same
  capability. Disagreement is a `FORM_CONFLICT` refusal, never a silent pick.
- Supplying **neither** is `MISSING_SELECTOR`.
- An alias resolves visibly; an alias owned by more than one capability is
  `ALIAS_CONFLICT` rather than a guess. A `{tool, action}` that names none of
  that tool's actions but one record's alias written `tool.action`
  (`system_control` + `restart_editor`) resolves to that record on `describe`
  and `execute` alike, and the reply says so (`resolvedFromAlias`, `migratedFrom`).
- Unknown selectors return `UNKNOWN_CAPABILITY` / `UNKNOWN_TOOL` /
  `UNKNOWN_ACTION`, each with `suggestions` and an executable `nextCall`.

### A success can carry warnings

A successful receipt's `warnings` name what the call left wrong. Every request
that spawns, moves or re-meshes editor-level actors, whichever capability did
it, has those actors checked in the plugin before it replies
(`McpChangeWatch`): one now sunk, floating, intersecting another or sharing a
face plane with one (z-fighting), a mesh slot on the engine's default grid
material, a text still reading "Text", a copy pasted onto its original. Play
In Editor caveats and engine warnings logged during the call land there too.
A reply sent after its handler returned (a long-running task) carries no
placement checks; `control_actor audit_placement` sweeps the whole level.

### Stating what should hold: `expect` and `require`

`options.expect` lists assertions the plugin judges once the call succeeds,
against the editor itself: relations (`Lamp on Table`, `A inside B`,
`A nextTo B`, `A against B` (its back to B), `A facing B`, `A near B within 50`), comparisons
(`Cube.location.z in 0..10`, `Lamp.LightComponent.Intensity > 1000`),
predicates (`A exists`, `A hidden`, `A visible`, `/Game/BP_Door compiles`) and
`noWarnings`, combined with `not`, `and`, `or` and parentheses. The receipt's
`expectations[]` gives each one's verdict (`ok`, `failed`, or `unknown` when it
cannot be observed yet), what was found, and for a failure the call that fixes
it; a failure also adds a warning. An expectation never fails the call it
judges: the change was made, and answering failure would hand back a
single-use consent grant and make a retry repeat it.

`options.require` lists assertions that must hold before the call runs. They
are judged on the game thread just before the handler: when one fails or
cannot be judged, nothing runs and the call answers `PRECONDITION_FAILED`,
naming each unmet requirement (a consent grant is handed back). Both lists are
part of the idempotency fingerprint, so a key resent with other assertions is
refused with `IDEMPOTENCY_CONFLICT`, never served the first call's receipt.

### Counting instead of reading: `aggregate`

`options.aggregate` counts a list in the plugin instead of sending it. The list
(`field`, default the largest list in the reply) comes back empty, and the
reply's `aggregate` gives its `total`; with `groupBy` (a field of the items,
such as `class`) each value's `count`, most common first, at most 50 groups
(`otherGroups` counts the rest), each with a `sample` of up to `sample` items
(0-10, default 3) named by their `name`, `label`, `actorName`, `assetPath`,
`path` or `id`. "How many actors of each class" is one call:
`{ ..., "options": { "aggregate": { "groupBy": "class" } } }`. It counts what
the call returned: a paged list counts its page, and `aggregate.note` says so,
so raise the call's own `limit` to count everything at once (the actor list
takes 1000). A reply without that list keeps its data and `aggregate.note` says
so. The aggregate is part of the idempotency fingerprint, as `expect` is.

### Many calls in one: `run_script`

`system_control run_script` runs a script of capability calls in one request,
in the S-expression grammar `read_graph_as_code` prints: `(let r
(control_actor.list :filter "Crate"))`, `(for c r.actors ...)`, `(if ...)`,
`(expect "...")` in the language above, `(return ...)`. The whole script is
checked before anything runs (capability ids, each call's parameters against
its contract, names bound before use). Each call then goes through the same
validation and pre-queue gate as a direct execute, for the same caller, except
consent: `run_script` asks for elevated consent, and every capability the
script calls that asks for consent must be listed in `destructive`, which that
one grant then covers. A failed call or expectation rolls the script back
through a restore point, as far as editor undo reaches (a Blueprint compile or a
level load clears the history; the reply says what was not undone).

A script that worked can be kept as a **recipe**: `save_recipe { name, summary,
script, paramNames }` checks it as `run_script` would and stores it under
`Saved/EngineWire/Recipes/`, and `run_recipe { name, args }` runs it as
`run_script` runs one. Search lists matching recipes beside the capabilities, under
`recipes` (at most three, only on an unfiltered first page, and only for a caller whose token holds the read scope, as `list_recipes` needs): each is `{ name,
summary, paramNames, verified?, nextCall }`, listed when its name and summary
name every content word of the request or at least two of them; its `nextCall`
describes `run_recipe`, which hands over the consent grant.

## Deprecation and removal behavior

Three distinct removal behaviors exist. They are not interchangeable.

### 1. A direct call to a canonical tool name

A `tools/call` whose `name` is not `unreal` is **not routed**. It returns a
bounded, copy-paste-executable `DIRECT_TOOL_CALL_REMOVED` receipt
(`McpNativeGatewayDirectCallMigration.cpp`, sent from
`McpNativeTransportGateway.cpp`). The receipt's `nextCall`
drills exactly one level:

| Situation | `nextCall` |
| --- | --- |
| unknown tool name | `{ "operation": "search" }` |
| known tool, no action | `{ "operation": "describe", "tool": "<tool>" }` |
| known tool with an action | `{ "operation": "execute", "tool": "<tool>", "action": "<action>", "params": { … } }` |

The migrated `params` are the original arguments with the nested `params`
wrapper flattened (top-level keys win) and the control fields `action`,
`subAction`, `params`, `operation` removed. Re-running the `nextCall` through
`unreal` completes the migration.

## Execute error codes

| Code | Raised by |
| --- | --- |
| `FORM_CONFLICT`, `MISSING_SELECTOR`, `ALIAS_CONFLICT` | form resolution |
| `UNKNOWN_CAPABILITY`, `UNKNOWN_TOOL`, `UNKNOWN_ACTION` | selector lookup |
| `UNDECLARED_PARAMETER`, `MISSING_REQUIRED_PARAMETER`, `INVALID_PARAMETER_VALUE` | schema validation |
| `NOT_CONNECTED` | the editor is unreachable |
| `UNREAL_EXECUTION_ERROR` (or the handler's own code), `OUTPUT_SCHEMA_VIOLATION`, `RESULT_TOO_LARGE` | dispatch and output validation; a result over 100k chars whose size is one top-level list comes in pages instead, each reply's `page.nextCall` reading the next |
| `PAGE_CURSOR_EXPIRED`, `PAGE_CURSOR_MISMATCH` | `options.pageCursor` unread for 5 minutes or never issued; or sent with another capability or params |
| `DIRECT_TOOL_CALL_REMOVED` | a `tools/call` on a non-`unreal` name |

Authorization refusal codes are shared verbatim with the plugin and are
documented in [`security-and-receipts.md`](security-and-receipts.md).

A request past the native transport's per-client rate limit (the plugin settings
`MaxClientRequestsPerMinute` and `MaxClientToolCallsPerMinute`) is answered with
JSON-RPC error `-32000`, `data.errorCode` `RATE_LIMITED` and `data.retryAfterSeconds`,
and a `Retry-After` header.
